# GPU 调频与交互卡顿修复

## 2026-11-02：重整 Metal 前端与渲染验证

对照 [dada 的 GPU 实现](https://github.com/superboyyy/hakios-arm64e-dada/tree/f1ae906fcc43ba8f763663257724ba938fb820ab/gpu2)
和 [AdrenoMetal 171d30b](https://github.com/UniXNU/AdrenoMetal/tree/171d30b0400cbcdb26d304a908b552781ef840da)。
houji 已固定 metal2vulkan `219f0136`，比 dada 的 `720ef1c` 基线更新；本次保留该运行时，
先重整前端的采样/resolve 和纹理复制入口，避免同时更换内核、编译器与驱动而失去对照。

- 纹理、管线与 render pass 使用一致的采样策略。默认测试单采样，减少抗锯齿；原请求模式保留作对照。
- resolve 不再一律重定向：Load 和 StoreAndResolve 保留源内容并在 pass 后复制；涉及的 Objective-C 资源持有到原命令完成。
- 补齐按 slice 和 mip 范围复制的 Metal 方法，验证完整范围后再编码，并处理 cube 的六个面。
- 差分测试实际触发了缺失的 `functionConstantsDictionary` 方法。补齐真实反射数据及 C ABI，
  保留常量名称、类型、索引和 required 属性；同时按 Metal 的实际 `required` getter 适配，
  不照搬参考实现中只提供 `isRequired` 的声明。
- 增加真实主机 GPU 像素检查。原生 Metal、Vulkan 原采样及单采样均通过 11 个场景；
  这些场景覆盖定义好的输出，不把未写入纹理的颜色当作正确性参考。
- 提取自本机 iOS 16.7.16 的原版 QuartzCore 半/单精度七点模糊函数，在原生 Metal 与
  当前翻译运行时上分别完成 6 轮、每轮两次渲染，均符合独立卷积参考，最大误差低于 0.001。
  这是有限的 shader 正确性证据，不能扩展到所有系统 shader、Turnip/A750 或紫色区域已修复。
- 另从历史专门化记录构造 12 个双附件 QuartzCore 合成用例，双方未记录的常量均显式置零。
  原生 Metal 和当前运行时的输出中 10 组逐字节相同，另外两组分别只有 1/44 个通道差 1 个
  8 位量化单位；没有复现大面积错误。用例是合成输入，不是设备问题帧的逐 draw 回放。

首轮设备候选关闭会暂停渲染线程的 CPU 采样器，保留有界阶段记录。实机动画、颜色、
持续帧间隔及撕裂仍待验证，不能将主机结果记为设备修复。

### 缓冲池候选：所有 App 共用的分配路径

r264 仍记录到 BoAlloc 34.951 ms（其中核心处理最高 34.614 ms）和显示等锁 22.084 ms。
对照固定的 Adreno740 `5c8c1453`，上游曾在逐页切换缓存属性时观察到大对象分配
90–130 ms 的停顿，使用保留的 WC 池避免每个 BO 反复切换。此记录解释了采用该设计的
依据，并不证明本机所有长停顿都来自缓存属性。

本机新增显式测试参数 `gpool=<MiB>`，默认关闭，最多 512 MiB，单个 BO 仍限 256 MiB。池由 XNU 从其管理的
RAM 申请并保留，逐 CPU 页核对物理连续性与输出地址范围；不扩大 GPU VA 窗口，
不修改设备树保留区，也不占用固件和显示缓冲区。每个对象独占完整 CPU4K/CPU16K 页，
包含逻辑长度外的填充；复用前重查 WC 属性并全部清零。池满时沿用原分配路径。
CPU 映射 lease、GPU fence、TLBSYNC 及失败隔离规则全部保留，导入 IOSurface 不进入池。
池的缓存属性转换不确定时保留整块内存，不发布给客户端。

候选启动会先通过原有一致性自检，再使用池完成两轮内核客户端打开、CPU 映射、
已知图像回读和关闭/复用，成功后才注册桌面加速器。主机检查覆盖 4K/16K 边界、
池满回退、碎片合并、元数据耗尽、失败转换和 CPU/GPU 引用退休，不代替设备测试。
固定日志新增池命中/回退/占用计数。r265 已运行：1681 次命中、27 次回退、
使用峰值 226 MiB，但用户反馈动画基本不变，文字乱码与紫色仍在。
分配核心处理均值约 0.286 ms，仍有 30.914 ms 的长调用；不能宣称动画修复。

## 为什么上游 1 GiB 仍能流畅运行

窗口容量仅约束可同时映射的 GPU 地址，不决定每帧提交、着色器翻译或显示同步成本。
对照固定版本源码，可以确认以下差异；这些差异是后续移植依据，尚不能分别确定本机卡顿所占比例。

| 路径 | 上游证据 | houji 当前情况 |
| --- | --- | --- |
| 缓存一致性 | [sheng 的 `coherenceProbe`](https://github.com/UniXNU/UniXNU-sheng/blob/08cde20edc3254ed6f7df8d0f5384fb887786e8f/package/GpuPowerProbe.cpp) 实测 CPU 脏缓存到 GPU、GPU 写入到 CPU 驻留缓存两个方向，通过后才开启 I/O coherent 快路 | r246 双向实验、r247 八次 WB 图像回读通过；r248 每次启动复验后启用 WB/inner-shareable 导入，缓存发布平均约 0.014 ms，桌面滑动与后台任务体感改善。NC 仍维护，未移除提交与显示依赖 |
| 提交批量 | [Adreno740 ABI](https://github.com/UniXNU/Adreno740/blob/5c8c1453c67d6ef6b10ec43ab1f8fc570a2f33e1/NativeAdrenoABI.h) 支持每次 128 个命令缓冲，配套实现也调整了存储 | r235 已运行 Query 能力协商的 128-IB 批量接口，1582 次超过 16 段、最大 120 段；保留旧 416 字节接口、缓存保护与 fence 生命周期，用户反馈整体更流畅 |
| 预热 | [sheng 的验证记录](https://github.com/UniXNU/UniXNU-sheng/blob/08cde20edc3254ed6f7df8d0f5384fb887786e8f/porting.toml) 有系统库预热和交互避让 | r232 已安装内嵌本机 iOS 16 的 138 条库路径，经实际文件筛选为 135 个库；r235 完成 26 个，持续交互会让预热等待 |
| 硬件与系统 | sheng 为 SM8550 / A740、iPadOS 17.7.11 | houji 为 SM8650 / A750、iOS 16；驱动能力、surface 格式及系统 shader 工作负载不同 |

上游也记录了客户端资源申请被拒绝的情况，不能把一次演示视为所有应用与渲染路径都没有缺陷。
其软件通知频率和日志中的提交速率也不能替代本机面板的 TE/vblank 测量。
扩大窗口可以缓解地址压力，但 r231 的实际反馈已经说明它不能单独修好颜色、文字和交互。

## 已修改的运行路径

### 2026-10-31 教程复核与后续候选

对照 [GPU 适配指南](https://unixnu.com/zh/porting/gpu) 和[平台/显示前置条件](roadmap.md#按依赖推进)：

- 采用 [Adreno740 `5c8c1453` 的句柄索引](https://github.com/UniXNU/Adreno740/blob/5c8c1453c67d6ef6b10ec43ab1f8fc570a2f33e1/NativeAdrenoHandleIndex.h)，替换用户客户端逐项查找；空槽提示和存活计数同时避免每次分配扫描整张表。保留单连接递增句柄、CPU 映射 lease 和失败隔离，并拒绝句柄溢出。CPU4K/CPU16K 主机回归覆盖 4096 对象耗尽/复用、哈希碰撞删除、旧句柄、导入和失败释放。r239 已运行该实现；没有相同工作负载下的对照，不能据此量化性能提升。
- 指南文字提及 16384 对象，但其源码索引所固定的 `4e0314df` 仍使用旧扫描实现；已另核对实际 `5c8c1453`。本机暂保留 4096 上限，不能只增大客户端数组而忽略共享 VM 表、span 容量和额外元数据成本。r238 保留的主槽位峰值为 957，此次没有触及对象上限的证据。
- sheng 的连续 WC 物理池与渲染进程的 1 GiB **虚拟窗口**是两项资源。r264 及之前每个自有 BO 独立申请；新增的本机有界 WC 池候选及 CPU16K 生命周期规则见上文，尚不能记为设备性能改善。
- 本机尚使用完整映射检查；不能仅为速度切成 Exclusive 调用。必须先证明自有页与固件/scanout/导入页不相交，导入页缓存类别兼容。常规提交的重复 TLBI 已移除；unmap 失效、fence 和失败隔离仍保留。
- r238 的七个异步编译入口计数均为 0（保留的桌面进程），因此继续检查实际同步编译、缓存发布、CPU 复制及调度时间，不以“加入异步”推断动画改善。软件 120 Hz 通知与 GPU 完成均不等于面板同步。
- Preferences 新增专用的 256 MiB VA 槽位及显式客户端名单，用于修复通知页无法取得 Metal 设备这一前提；原四个窗口不变。它不预分配 256 MiB RAM，也不提供独立硬件页表，r239 已确认连接成功、通知页可进入，本轮没有新增 Preferences IPS；仍有其他渲染缺口。

已知图像回读需要覆盖透明清除、混合、文字纹理与实际 surface 格式；单次 GPU 图案写回只证明命令/内存通路。粉色和文字错误仍未解决。

### 上游缓存一致性自检的本机移植

`HoujiGpuCoherenceProbe.inc` 移植锁定 sheng 版本的双向实验，在原有 GPU/UFS 共存验证完成后运行。诊断模式 `houji_gpu_runtime=4` 完成后返回 Recovery，不启动 Metal 用户客户端，也不打开 `native_adreno_io_coherent`；私有模式 5 的后续桌面对照见下文。默认桌面模式仍为 3。

实验独占四个完整 CPU16K 页面，映射成 GPU WB/inner-shareable；使用已验证 ring 上两条固定 CP_MEMCPY。先证明至少 48/64 个源缓存行在 DRAM 中仍是旧数据，再检查 GPU 是否读到全部 1024 个新值；随后保持目标页面的 CPU 缓存行，检查 GPU 写入是否能由 CPU 普通读取完整观察。原 CPU 映射和无缓存别名均检查实际页属性与物理地址。测试不经过会清理所有映射的常规提交入口，以免自检本身消除脏缓存条件。

脏行不足、映射属性变化、部分匹配、超时和清理失败均不能判定通过。固定命令只访问这 64 KiB 自有内存；失败保留所有引用，30 秒独立保护返回 Recovery。主机检查只验证命令边界与判定逻辑，硬件结果另记设备测试。

r246 已通过这两个方向的硬件实验。后续自检增加已验证 CP_BLIT 的八次交替 WB 目标写入，只改固定输出地址，并检查红色像素、CRC、DRAM 视图和 CPU16K 页内保护字节；不把 CP 拷贝通过直接推广到所有渲染路径。

即使此基础实验通过，也不能直接省略所有 imported IOSurface 的维护：上游记录过 GPU 可写 WB 导入在渲染结束清理阶段停滞，其 `importedUntouched` 另有 CPU 不访问的假设。本机仍需逐类验证真实资源访问、已知图像和连续交互，然后才能启用相应优化。

r247 已通过两个 WB 目标的八次固定图像回读。新增私有诊断模式 5 在每次启动完成全部自检后，才将导入缓冲区映射为 WB/inner-shareable 并进入短测桌面；默认模式 3 仍保留原策略。它不采用上游 `importedUntouched` 的 NC 导入免维护假设，因为本机 CPU presenter 会读取这些像素。NC、外部共享或未验证模式仍走维护，原提交等待和显示依赖均保留。CPU4K/CPU16K 主机检查覆盖实际 map/publish/complete/unmap 回调与映射引用；不能据此宣称完整桌面更快或渲染正确。

## 8 GiB RAM 与 GPU 分配不足

r227 的系统 RAM 配置为 8 GiB，但 NativeAdreno 使用共享 GPU 页表和有限地址窗口；
该版本的 backboardd 仅能在 1 GiB 窗口中映射资源。系统剩余内存、GPU 窗口总空闲量和最大连续空闲块是不同的量。
日志中 backboardd 的地址高水位接近窗口末端，是继续检查地址压力的依据，不能用它计算实际已用字节。
其他客户端还有槽位限制，r227 的 AegirPoster 因此被拒绝 22 次；扩大系统 RAM 不会解除这项限制。

对照 [Adreno740 当前地址布局](https://github.com/UniXNU/Adreno740/blob/main/NativeAdrenoPublish.cpp)，
上游也为渲染服务保留 1 GiB，并未提供可直接照搬的每进程 GPU 页表切换。
[metal2vulkan 固定版本的内存池](https://github.com/steelbrain/metal2vulkan/blob/219f01365dc4c8eb346816c405b5b17403793764/crates/metal2vulkan-runtime/src/memory.rs)
通常按 64 MiB 申请新池块，并保留空闲块以减少帧间抖动。
在受限地址窗口中，即使实际资源只需 12 MiB、尚有 24 MiB 连续空间，申请一个完整池块也可能失败。
这解释了一个可修复的失败条件，不等于已证明 r227 的每次 OOM 都由它造成。

r227 后候选在真实分配函数中增加以下处理：同一堆的所有内存类型回收已空闲池块；
仍无法申请常规池块时，按实际资源大小创建独立块，并随资源释放。
不缩小资源、不释放活跃块，不跳过未完成命令的退休规则；DeviceLost 继续原样返回。
Turnip 报告的堆大小同时限制到客户端地址窗口，分配失败记录 request/free/largest，便于区分耗尽和碎片。
这些回收措施不替代地址扩容；后续 r228 内核候选另将总页表覆盖扩至 4 GiB、主渲染窗口扩至 2 GiB，详见[GPU 地址空间核对](gpu-address-space.md)。每进程页表、跨进程资源和客户端槽位仍需后续开发。

预热对照 [AdrenoMetal](https://github.com/UniXNU/AdrenoMetal/blob/f0c317742b08379bab3239b5558dcc16f8c22f66/PrimeShaders.h)：
新 bundle 内嵌 138 个系统 metallib 路径，优先 QuartzCore、RenderBox 和 CoreUI，避开昂贵的目录扫描；
完成标识包含运行时源码身份和 Turnip UUID，更新组件后重新预热。
补齐零值函数常量、关联函数与光栅化 pipeline，记录进度和拒绝原因；
遇 OOM 停止当轮并保留未完成状态，下一次启动可以重试。
这些能减少首次翻译/编译开销，但实际绘制时不同常量、附件格式和 pipeline 状态仍可能新编译；
预热也不能修复面板同步、GPU 地址限制或所有错误混合。

## 频率设置

`houji_dvfs` 的 bit 1 开启 GPU governor；现有 `houji_dvfs=3` 同时开启 CPU 和 GPU。
新增参数是 **`gpu_max_mhz`**，单位 MHz，选择上限而非固定运行频率。

| 参数 | 行为 |
| --- | --- |
| 未设置、`0` 或 `903` | 开放全部工厂档位，最高 903 MHz |
| `500` | 显式选择历史 500 MHz 上限，仅用于对照 |
| `680` | 允许 governor 在 231–680 MHz 的工厂档位间选择 |
| 表内非整档，例如 `650` | 向下取 629 MHz，绝不超过请求上限 |
| 小于 231、大于 903 或无效无符号值 | 拒绝该值，记录日志并回到工厂 903 MHz 上限 |

START 阶段仍投票到既有的 500 MHz 启动档。上限在 governor 建立计数基线后开始执行，
因此低于 500 的设置不是对启动全过程的硬上限。governor 关闭或线程启动失败时保持启动档。
500 MHz 只用于已有 HFI 启动交接，不能据此限制运行时性能。运行默认上限为工厂最高档，
不锁频、不新增电压票。r242 的旧策略在触控一秒内强制提升到有效上限；当前候选改为有实际活动时提供有效上限 60% 的工厂档位下限，真实高负载仍能升到完整上限，空闲不因触控续期而保持高档。唤醒的 50 ms 内至少提高到 578 MHz 或当前频率的两倍，
均服从温度上限。工厂档位存在不等于新系统的散热策略已通过长期验证。

当前有效的 UEFI 启动参数位于
`uefi/overlay/Platforms/Xiaomi/houjiPkg/Application/HoujiStorageProbe/HoujiStorageProbe.c`
的 `BaseBootArgs`，已经显式写入 `gpu_max_mhz=903`。测试其他上限时**替换同一个值**，
重新构建配套的内核、UEFI 和启动载荷；只改 `board.toml` 不会修改这条固定启动路径。
包含最后的触控交接参数时命令行有 606 个 ASCII 字符，连同 NUL 占 607/608 字节。
新增长度检查会拒绝超限启动，避免静默截断；不要继续追加参数或重复设置同一键。

检查 `HOUJI GPU OPP`、`HOUJI OPP SNAPSHOT` 中的 `cap-MHz` 与每档
`HOUJI OPP RESIDENCY`，并确认 `failed=0`、`bad=0`。这些仍是请求与 ACK 驻留。

CPU framebuffer 复制同样必须覆盖生产者之后已经提交的 GPU 写入，再持 issuer 锁完成读取。
尚无每个 surface 的完整 GPU 写依赖追踪，不能只看到生产者 fence 完成就复制可能被后续工作改写的内存。

## 温度与亮度

`HoujiThermal.inc` 独立线程每 100 ms 读取本机 TSENS v2 TM 窗口，按设备树的传感器分组取最高结温。
GPU 使用本机 95°C / 5°C 滞后；CPU 也暂以 95°C 限制，低于设备树的 108/110°C 临界点。
到阈值每次收窄一档，110°C 立即最低档；低于 90°C 每秒恢复一档。
VALID 短暂失效时按小米驱动行为有界重读，每组最多 20 ms；仍无有效读数或数据超界就最低档，
CPU 与 GPU 的触控提升都不能覆盖温度限制。固定快照保留各组温度峰值、失效次数和失败原始值。
读取不改 TSENS 校准或控制寄存器，尚未实现 PMIC 机身/电池温度和紧急关机。
若 iOS 日志持续 `valid=0`，必须修复传感器交接，不能为了性能绕过此限制。

r242 的 5 组最终无效采样均为 0，CPU 域最高结温分别为 90.7/98.1/96.6/96.9°C，GPU 为 85.3°C。其中 CPU 域 1 最后 cap 为 1/29；不能把这轮发热归因于无效温度读数。GPU 903 MHz 请求驻留约 180.731/326.986 秒（55.27%），最后一段忙碌比例仅 70‰，仍因触控下限请求顶档；该单次忙碌值不是整轮平均。

候选同时将 CPU 的触控下限从工厂最高档改为 60%，并要求该域最近有负载。连续 12 个低于 10% 负载的采样（约 240 ms）后，即使其他域仍有触控或帧活动，也解除该域的交互下限；负载上升时继续立即调高，工厂 LUT 与温度限制不变。这只修正强制升频的策略，不能证明完整功耗管理或流畅性已达标。Recovery 中电池传感器从 40.9°C 降至约 38.8°C，属于退出后的降温观察，不是新候选的效果。

本轮命令缓冲的提交到完成均值 17.934 ms、GPU 时间戳均值 5.687 ms；缓存发布均值 2.768 ms/提交。命令缓冲不是画面帧，不能用这些数反算 FPS。Recovery 的模式列表包含 120 Hz，但也不证明 XNU 下的面板当前刷新率。[上游显示指南](https://unixnu.com/zh/porting/display)要求分别记录请求刷新率和测得时序；本机仍需核对 DPU/DSI/TE，不能直接套用 SM8550 的双 DSI 寄存器和直接扫描开关。

当前候选在固定日志前缀保留显示通知、完成复制、缓存维护、队列等待与最近四个时间窗口；复制计时覆盖最终 store barrier，只在复制成功后累计完成次数。另保存 CPU 最近完整 5 秒窗口，即使运行超过旧历史的 240 秒也可回收。均只复制内存中的统计，不访问硬件，不改变原有帧引用或 GPU fence 规则。这些仍不是面板 vblank 测量。

`HoujiBacklight.inc` 绑定本机 DSI0（`0x0ae94000`）和 n3 面板：正常亮度最大 2866、最小非零 25，
不进入 HBM。它用 DCS `0x52` 读取初值，`0x51` 发送高字节在前的亮度，接入 CoreBrightness 的
`IODisplayParameters` / `FadePeriod`。独立工作循环合并连续请求并做渐变，每个命令有 50 ms 上限，
失败后停发；不占用显示复制线程做长忙等。DMA 完成只证明命令交出，不能代替面板实际亮度测量。
内核保留真实 `HoujiBacklight` 类型，仅扩展该对象的用户空间兼容查询和 backboardd 的受限亮度属性授权。
对照小米官方显示驱动补充清除旧回包、检查新回包字节数和有界等待，并修正中断状态掩码，避免误清其他帧事件。
r227 固定快照确认 DSI 初值回读、服务注册成功，但 210 次属性请求均在参数解析时被拒绝。
新候选兼容直接 OSNumber、一层 value 字典以及附带元数据，保留亮度和渐变范围校验；
同时记录参数形状和原始数值。r229 用户确认调光有响应，DSI 日志无错误；仍有被拒绝的属性请求。
完整亮度范围、连续拖动及熄屏/唤醒仍待验证。

匹配的 Metal/Turnip 候选已在 r232 安装并完整回读，r233、r234 均进入桌面。r234 用户仍很卡且粉色复现；保留错误不能证明整个运行期间没有 OOM，也不能把不完整预热当作预热完成后的性能对照。
r234 将首次绘制后的提前收尾时间从 120 秒延至 300 秒，保留 360/420 秒两层上限。缓存记录为 16/135 个库、225 个 pipeline，仍处于等待安静状态；最终日志快照不能证明完整采样时长。
r235 保存的 2538 次内核提交含 59341 段命令，平均内核提交 3.694 ms、缓存发布 2.923 ms；批量优化减少重复提交，没有移除缓存维护。2506 个 Metal 完成记录平均 19.567 ms、最大 471 ms；GPU 时间跨度平均 6.454 ms，其中可能包含主机分批间的空闲。预热完成 26/135 个库、1165 个 pipeline，仍不是完整热缓存结果。渲染颜色未通过验收。
组件身份变化会使旧的预热完成标识失效，
shader 缓存是否命中仍取决于各层内容键，先观察预热日志与 OOM，
再在相同分辨率和软件刷新设置下分别记录冷/热缓存交互。以默认 903 MHz 候选验证
传感器读数、实际调频请求和持续交互。需要隔离频率影响时再显式以 500、680 MHz 做对照，
不再将 500 MHz 当作默认正确配置。每轮执行解锁、连续左右滑动、设置列表滚动、
打开/关闭同一应用、最近任务、键盘输入，重复三轮并保留冷启动与缓存已热两种情况。
记录提交时间、GPU 时间戳（不可用就标记不可用）、命令错误、复制耗时、队列等待与
调频驻留；有温度/功耗测量时一并记录。相同动作的呈现完成间隔应比较 P50/P95/P99，
当前累计计数无法反推出这些分位数，需要补充逐帧记录或外部拍摄。CPU 复制数不能当作面板 FPS。

持续卡顿、黑屏、紫色阴影或字体异常任一仍存在，都不能将相应功能标记为完成。
直接 DPU scanout、BO 池及更完整的 CPU/GPU 缓存一致性仍需独立板级工作；新增结温策略不等于完整电源管理。

## 待完成 fence 的锁外观察

[r282 的命令与锁记录](device-tests.md#r282--卡顿复现等待锁与命令阶段同时回收)显示，
动画期间存在明显长于 GPU 时间跨度的完成延迟。候选选择性采用
[Adreno740 dd43abd](https://github.com/UniXNU/Adreno740/commit/dd43abd05ce01f2734ff616f695aaa24d4e5c1b2)
的等待循环：pending 时不每隔 100 µs 取得 issuer mutex，真正观察完成或超时后仍加锁验证。
本机 ring acquire 回调包含硬件状态检查，不能直接放到锁外；因此先验证同一保留分配中
完成字的精确 PA 与 Normal-NC 映射，仅将其作为负向提示。未知 fence、资格不足和设备停止
均回退原有检查，不绕过缓存维护、错误传播或资源退休。`HOUJI FENCE POLL` 记录实际跳过
锁的 pending 次数，`HOUJI FENCE HINT` 报告启动资格。r283 已实测跳过 99,963 次 pending
争锁，但用户反馈动画没有改善，提交到回调的平均值与 P95 也没有下降，见[本轮结果](device-tests.md#r283--锁外轮询已生效动画未改善)。这项优化不能作为动画问题已解决的依据。

2026-11-01 另核对 UniXNU `6790e7ce` 的 Turnip Darwin 补丁；其等待成功后仍同步回收 retired BO。
该路径可能包含清理成本，但当前缺少本机对应阶段证据，未将它当作已证实根因。

## 合成线程的提交前空档

r286 的设置动画与命令阶段按 uptime 对齐后，出现约 79–110 ms 的提交空档。
已记录的 GPU 等待和管线创建不能覆盖整个空档；命令创建至提交时间还包括调用方工作，
不能将全部时间计作驱动编码。r287 用户仍反馈设置比其他应用更卡。

AdrenoMetal 的[合成线程采样](https://github.com/UniXNU/AdrenoMetal/commit/77e6694)
同时观察命令内和命令间的调用栈；[独立编码线程](https://github.com/UniXNU/AdrenoMetal/commit/0dd1516600e1c0adc22494860d58a18988834940)
记录的是上游特定滑动测试约 61 → 67 FPS，不能转为本机 120 FPS 结论。
本机先加入 `NativeMetalCpuProfile.h`，定位剩余空档后再决定编码线程的接入范围。

`tools/build-metal.py --gpu-stage-trace --gpu-cpu-profile` 显式开启此诊断；默认关闭，
只允许 backboardd 的首个 `com.apple.coreanimation` 线程，每 10 ms 采样一次，最多 90 秒，
文件 `cpu-profile.log` 不超过 4 MiB。采样时不分配、不加用户锁、不解符号、不写文件；
栈通过有界 VM 读取，保留线程端口直到采样结束，失败路径仍恢复线程。
绑定、绘制、结束编码、提交和等待带阶段标记；记录使用与 GPU 阶段相同的 uptime 时钟。
主机检查实际执行 Mach 暂停/读取/恢复和坏边界路径，但不证明 iOS 时序、颜色或性能。

`tools/analyze-cpu-profile.py` 可用 `--from-uptime` / `--to-uptime` 选取动画空档。
统计是离散调用栈观察，采样自身会扰动调度，不能当作 CPU 使用率或帧率验收。
